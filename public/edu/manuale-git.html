Guida pratica all'uso di Git da linea di comando

I comandi fondamentali per gestire il controllo versione nei tuoi progetti

1. Working Directory

La cartella dove scrivi e modifichi il codice sorgente.

2. Staging Area

L'area dove sposti le modifiche per che vuoi aggiungere nel commit.

3. Local Repository

L'archivio locale sul PC che contiene la cronologia dei commit (la storia del progetto).

4. Remote Repository

Il server remoto che utilizzi per condividere il codice. Di default viene chiamato origin.

1 Configurazione e setup iniziale

Prima di iniziare a lavorare con Git sul tuo computer, devi configurare la tua identità di sviluppatore. Questa operazione va fatta una sola volta per macchina.

# Imposta il tuo nome e cognome
git config --global user.name "Nome Cognome"

# Imposta la tua email (utilizzata su GitHub / GitLab)
git config --global user.email "nome.cognome@studente.it"

Ottenere o inizializzare un progetto

A seconda di come inizia il tuo lavoro, segui uno dei due scenari:

Caso A: scaricare un repository remoto già esistente

git clone https://codeberg.org/nome_utente/nome_repo

Caso B: Inizializzare una nuova cartella locale come repository Git

cd percorso/della/tua/cartella
git init

2 Il flusso di lavoro locale (add & commit)

Ogni volta che scrivi nuovo codice o modifichi file esistenti, segui questa sequenza standard di lavoro:

Passaggio 1: Verificare lo stato dei file

Usa questo comando frequentemente per sapere in quali condizioni si trovano i tuoi file (modificati, non tracciati, pronti per il commit).

git status

Passaggio 2: Spostare le modifiche nella Staging Area

Seleziona i file che intendi salvare nel prossimo punto di ripristino.

# Aggiungi un singolo file specifico
git add index.html

# Oppure aggiungi TUTTE le modifiche presenti nella cartella corrente
git add .

Passaggio 3: Salvare le modifiche (commit)

Crea una "fotografia" dello stato attuale del codice. Accompagna sempre il commit con un messaggio chiaro e sintetico.

git commit -m "Aggiunta gestione dell'autenticazione utente"

Passaggio 4: Consultare lo storico dei salvataggi

# Visualizzazione sintetica dei commit
git log --oneline
# Visualizzazione sintetica dei commit con grafo
git log --oneline --graph
Best practice per i commit

Fai commit piccoli, frequenti e focalizzati su una singola funzionalità o correzione. Un buon messaggio descrive cosa è stato fatto e perché.

3 Sincronizzazione con il remote

Per lavorare in team o mantenere un backup su internet, devi sincronizzare il repository locale con quello remoto.

Scaricare gli aggiornamenti dal server (pull)

Prima di iniziare a scrivere nuovo codice o prima di inviare le tue modifiche, scarica i commit aggiornati inviati dai tuoi compagni:

git pull origin main

Inviare i propri commit al server (push)

Trasferisci i tuoi salvataggi locali al repository remoto per renderli visibili al team:

git push origin main

4 Gestione dei branch e merge

I branch (rami) ti permettono di sviluppare nuove funzionalità in isolamento senza rischiare di danneggiare il codice funzionante presente nel ramo principale (main).

Creare e passare a un nuovo branch

Usa la sintassi moderna git switch per creare un nuovo ramo e spostartici immediatamente:

git switch -c feature-login

Spostarsi tra Branch esistenti

# Torna al branch principale
git switch main

# Torna al branch di sviluppo
git switch feature-login

Unire le modifiche (merge)

Quando hai completato e testato il lavoro sul ramo secondario, uniscilo nel ramo principale:

  1. Spostati sul ramo di destinazione: git switch main
  2. Esegui la fusione: git merge feature-login
git switch main
git merge feature-login

Eliminare un branch completato

git branch -d feature-login

5 Concetti indispensabili e risoluzione conflitti

Il file .gitignore

Non tutto deve finire su Git. File compilati, cartelle di dipendenze pesanti e dati sensibili vanno ignorati.

Crea un file chiamato .gitignore nella radice del tuo progetto e scrivi i pattern da ignorare:

# Dipendenze Node.js / Python
node_modules/
__pycache__/

# File di configurazione IDE
.vscode/
.idea/

# File compilati ed eseguibili
*.class
*.exe
*.out

# Credenziali e chiavi private
.env

Risoluzione dei conflitti di merge

Un conflitto si verifica quando due persone modificano le stesse righe di uno stesso file e Git non può decidere in autonomia quale versione mantenere.

Come risolvere un conflitto:
  1. Apri il file segnalato in conflitto dal tuo editor di testo.
  2. Individua i marcatori visivi inseriti da Git: 
    <<<<<<< HEAD
Codice del tuo branch corrente (es. main)
=======
Codice del branch che stai unendo (es. feature-login)
>>>>>>> feature-login
  3. Cancella i marcatori e modifica il codice mantenendo solo la versione corretta (o una combinazione di entrambe).
  4. Salva il file, aggiungilo in staging e completa la fusione con un commit: 
    git add nome_file.js
git commit -m "Risolto conflitto di merge su nome_file.js"

Annullare modifiche locali

Se desideri annullare le modifiche locali apportate a un file non ancora aggiunto alla staging area:

git restore percorso/del/file

Se togliere delle modifiche locali dalla staging area:

git restore --staged percorso/del/file

6 Tabella Riassuntiva dei Comandi

Comando Descrizione
git status Mostra lo stato del workspace e della Staging Area.
git add . Aggiunge tutti i file modificati in Staging Area.
git commit -m "msg" Salva le modifiche nel repository locale.
git push origin main Invia i commit locali al server remoto.
git pull origin main Scarica e integra i commit dal server remoto.
git switch -c ramo Crea un nuovo branch e ci si sposta sopra.
git merge ramo Unisce il ramo specificato in quello corrente.
git restore file Annulla le modifiche non ancora messe in staging.
