Paradigmi di comunicazione

I diversi modelli di interazione tra client e server nel web

1 Guidati dal client (client-driven)

L'iniziativa della comunicazione parte sempre dal client.

Richiesta-risposta (request-response)

È il paradigma più comune del web. Il client invia una richiesta a un server e attende una risposta. La connessione viene generalmente chiusa dopo la risposta. È un modello stateless, nel senso che ogni richiesta è indipendente dalle altre.

  • Tecnologie: HTTP/HTTPS, il protocollo su cui si basa l'intero World Wide Web.
  • Utilizzo: sicuramente il paradigma più diffuso e fondamentale per le applicazioni client-server. Tutte o quasi tutte le applicazioni web utilizzano questa modalità di comunicazione, a volte combinandola con le altre.

Polling

Il client contatta il server a intervalli regolari per verificare se ci sono nuove informazioni. È semplice da implementare ma molto inefficiente, in quanto genera molto traffico di rete inutile se non ci sono aggiornamenti frequenti.

  • Tecnologie: HTTP/HTTPS.
  • Utilizzo: notifiche, chat, grafici che si aggiornano in automatico.

Long polling

Una versione ottimizzata del polling. Il client invia una richiesta al server, ma il server la tiene "in sospeso" finché non ha effettivamente nuove informazioni da inviare. Una volta inviata la risposta, il client ne effettua immediatamente un'altra. Riduce la latenza rispetto al polling tradizionale.

  • Tecnologie: HTTP/HTTPS.
  • Utilizzo: notifiche, chat, grafici che si aggiornano in automatico.

2 Guidati dal server (server-driven)

È il server a poter iniziare la comunicazione verso il client.

Server-Sent Events (SSE)

Il client stabilisce una connessione persistente con il server, attraverso la quale il server può inviare dati al client in qualsiasi momento. La comunicazione, però, è monodirezionale: solo dal server al client. È più leggero dei WebSocket ed è ideale per aggiornamenti "in tempo reale" che non richiedono un input dal client sulla stessa connessione.

  • Tecnologie: EventSource API in JavaScript.
  • Utilizzo: notifiche, aggiornamento di feed di notizie, risultati sportivi in diretta.

3 Bidirezionali

Entrambe le parti possono iniziare la comunicazione in qualsiasi momento su una connessione aperta.

Canale di comunicazione bidirezionale

Un canale di comunicazione full-duplex (bidirezionale e simultaneo) tra client e server con una latenza generalmente bassa.

  • Tecnologie: TCP, UDP, WebSocket API (socket gestiti dal browser).
  • Utilizzo: applicazioni di chat, editor di documenti collaborativi.

Canale di comunicazione peer-to-peer (P2P)

Questo paradigma è specializzato per la comunicazione diretta tra i browser, senza che i dati debbano passare necessariamente attraverso un server centrale. Un server c'è comunque ma viene usato principalmente per il signaling, ovvero per coordinare la connessione iniziale tra i due peer e permettere loro di comunicare senza intermediari.

  • Tecnologie: WebRTC (Web Real-Time Communication).
  • Utilizzo: videochiamate, giochi multiplayer online, file sharing diretto tra utenti.

4 Basati su messaggi o eventi (message/event-driven)

Questi modelli sono fondamentali in architetture a microservizi e sistemi distribuiti, ma i loro principi si applicano anche alle applicazioni web complesse.

Publisher-subscriber (Pub/Sub)

Un componente (il publisher) invia un messaggio a un "canale" o "topic" specifico, senza sapere chi lo riceverà. Altri componenti (i subscriber) si iscrivono a quel topic e ricevono tutti i messaggi inviati su di esso. Questo disaccoppia fortemente i componenti del sistema.

  • Tecnologie: MQTT, Redis Pub/Sub.
  • Utilizzo: applicazioni IoT (internet of things).

Code di messaggi (message queuing)

Simile al Pub/Sub, ma focalizzato sulla consegna garantita di un messaggio a un singolo consumatore. I messaggi vengono inseriti in una coda (queue) e i processi worker li prelevano uno alla volta per elaborarli. È un modello fondamentale per le operazioni asincrone e per garantire l'affidabilità.

  • Tecnologie: RabbitMQ (AMQP).
  • Utilizzo: elaborazione di ordini, invio di email di conferma, processi di background lunghi avviati da un'azione dell'utente.
